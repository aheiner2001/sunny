Why Use AWS Lambda Instead of Querying Firestore in the Browser?

The three architectural pillars: Security, Device Battery/Performance, and Single Source of Truth.

Question 1: Why Not Just Read Firestore Directly in the Browser?

In a simple app, reading straight from the database into React feels easier. But for fleet reporting and payroll analytics, running it in the client browser breaks down quickly for three critical reasons:

Architecture Challenge Direct Browser Query ❌ AWS Lambda Backend ✅
1. Security & Payroll Privacy To calculate shift totals, the browser must download every raw timesheet of every coworker. Any user can open DevTools and see pay/hours. Lambda has secure Admin SDK keys in AWS Secrets Manager. It calculates the aggregated summary on the server and never leaks raw employee records.
2. Heavy Processing & Network Bandwidth Downloading 5,000 inspections, 1,000 shifts, and vehicle histories drains phone battery and bogs down a driver's mobile browser. Lambda crunches 3,600 lines of complex boundary math in AWS data centers in 200ms and sends back a tiny 2KB clean JSON summary.
3. Single Source of Truth If you change how overtime or break deductions work, you must update the website AND the email script separately. If their math differs, payroll is wrong! One single engine: The exact same math runs for the automated Sunday 2:00 AM email and the manager's live preview button.

Question 2: Why Did the Dates Look Like 1793602800000?

Computers measure time in Unix epoch milliseconds. In our preview modal, we printed period.start instead of formatting it into a human date like Nov 2, 2026.

Also, the Lambda sends back rich diagnostics that we haven't displayed yet:

  • Recommended Manager Actions: e.g., "Enable odometer in inspection checklist".
  • Per-Vehicle Status Breakdown: Which vans have missing readings vs. clean records.
  • Formatted Dates: Converting raw millisecond timestamps into readable calendar days.
