Authentication vs. Authorization (Who vs. What)

Welcome to Lesson 3! With your report preview math working smoothly, we now tackle one of the most critical security concepts in backend engineering: Authentication (AuthN) vs. Authorization (AuthZ).

1. The Fundamental Difference

The Security Checkpoint Analogy

Authentication (401 Unauthorized): Showing your passport or driver's license at an airport checkpoint. The officer verifies: "Are you really Sarah Connor?"

Authorization (403 Forbidden): Trying to enter the airplane cockpit with a passenger boarding pass. You proved who you are, but the system says: "You do not have permission to be in here."

  • 401 Unauthorized: Missing, expired, or invalid credentials. The server does not know who you are.
  • 403 Forbidden: The server knows who you are, but your account lacks the required role or permission (e.g. an employee requesting manager payroll reports).

2. The Critical Security Rule: Never Trust the Client

A Common Rookie Mistake: Accepting ?role=manager as a query parameter or in a JSON body. Any user could open Developer Tools and pass role=manager to see sensitive business data!

The server must determine the user's role independently:

  1. The client sends a credential in the HTTP header: Authorization: Bearer <token>.
  2. The server decrypts/verifies the token (or checks the trusted user record).
  3. The server reads the trusted role from that record.

3. How It Works Locally (Test Identities)

To experiment locally without needing a live Google cloud account, we use simple test tokens in our prototype:

  • Bearer token-manager → Authenticates as Morgan (Manager)
  • Bearer token-employee → Authenticates as Alex (Employee)
  • No header or bad token → HTTP 401
  • Alex requesting manager reports → HTTP 403

4. How Sunny Fleet Uses Firebase Auth in Production

In production, Sunny Fleet uses Firebase Authentication:

  1. On the frontend, the user signs in with Firebase Auth.
  2. The frontend retrieves an ID token: const token = await auth.currentUser.getIdToken();.
  3. The frontend sends it in the header: Authorization: Bearer ${token}.
  4. The backend uses the Firebase Admin SDK: 
    import { getAuth } from 'firebase-admin/auth';

const decodedToken = await getAuth().verifyIdToken(token);
const userId = decodedToken.uid;

// Look up role in the trusted 'users' collection or check custom claims:
const userDoc = await getFirestore().collection('users').doc(userId).get();
if (userDoc.data().role !== 'manager') {
  return res.status(403).json({ error: 'Manager access required' });
}
